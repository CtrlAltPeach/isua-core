## 3. Карточка абитуриента (Applicant Form Modal)

### 3.1 Структура вкладок (переупорядочивание)
**Новый порядок:**
1. **Основное** (ФИО, программа, статус)
2. **Документы и согласие** ← Переместить сюда (было ниже)
   - Чекбокс "Документы собраны"
   - Чекбокс "Согласие на зачисление"
   - Чекбокс "Особая квота" ← Новое
   - Чекбокс "Платно" ← Новое
   - Выпадающий список "Документ" (диплом/аттестат)
   - Паспортные данные (серия, номер)
   - Гражданство
3. **Баллы экзаменов**
   - Математика (база) — оценка 2-5
   - Математика (профиль) — баллы 0-100
   - Русский, Химия, Физика, Информатика, География — баллы 0-100
   - **Доп. баллы / ВИ** ← Новое, 0-100+ (может быть сверх 300)
   - Средний балл (авто-расчёт)
4. **Контакты** (телефон, email)
5. **Персональное** (прописка, ИНН, СНИЛС, заметки)
6. **История** (лог изменений)

### 3.2 Логика Математики (база vs профиль)
- [ ] **Взаимоисключающие поля:**
  - Если заполнен `mathBase` (оценка) → `mathProfile` должен быть disabled (серый, не редактируется)

- [ ] **При расчёте total_score:**

  - Если заполнен `mathProfile` → исключить mathBase (как сейчас)
  - Логика: студент сдаёт ЛИБО базу, ЛИБО профиль (не оба)

## 10-bis. Итерация 7 (NEXT — собрано 2026-06-13)

### 7A. Дашборд: «движение согласий за день» должно ОБНОВЛЯТЬСЯ, а не накапливаться
Сейчас метрики «новые согласия сегодня» / «забрали согласие сегодня» считаются из History
по событиям за день — поэтому если за день туда-сюда (забрал → вернул, подал → забрал),
счётчики накапливают КАЖДОЕ событие, а не итог дня.
- [ ] **«Новые согласия сегодня»** должны работать как «согласия на зачисление», но в рамках
  одного дня: показывать ЧИСТЫЙ итог за день (нетто), а не сумму всех переключений.
  - Если за день согласие забрали, а потом вернули → НЕ должно увеличивать «забрали».
  - Если за день согласие подали, а потом забрали → НЕ должно увеличивать «подали».
- [ ] Считать по конечному состоянию `consentToEnroll` на конец дня против состояния на начало дня
  (а не суммировать промежуточные переключения из History).
- **Где:** `src/app/api/stats/daily/route.ts` (consentGivenToday/consentWithdrawnToday).

### 7B. Карточка абитуриента: убрать вкладки → секции одна под другой
- [ ] Переделать `applicant-form-modal.tsx`: вместо вкладок все секции (Основное, Документы и
  согласие, Баллы, Контакты, Персональное) идут вертикально одна за другой, модал скроллится.
- [ ] История — отдельной секцией внизу или остаётся кнопкой-часами в таблице (НЕ вкладкой).
- (Решение пользователя: «все секции подряд + скролл».)

### 7C. Шифрование личных данных в БД (НЕ хэш — обратимое)
- [ ] Хранить чувствительные поля (паспорт серия/номер, ИНН, СНИЛС; возможно телефон/email)
  **зашифрованными** в БД (обратимо, ключ в env), расшифровка при чтении/показе.
- [ ] Защита на случай утечки дампа БД. Не путать с необратимым хэшем — данные должны
  оставаться отображаемыми авторизованному пользователю.
- (Решение пользователя: «шифрование в БД», а не хэш.)
- Открытые вопросы на старте: алгоритм (AES-256-GCM через node:crypto), хранение ключа,
  поиск по зашифрованным полям (паспорт в поиске? — возможно отдельный blind-index/хэш для поиска).

### 7D. Таблица: показывать кусочек заметки
- [ ] Добавить в таблицу колонку/превью **первой части заметки** (notes), с обрезкой.
- [ ] **НО таблица в целом всё ещё не устраивает** — рассмотреть несколько вариантов раскладки
  перед реализацией (карточки? настраиваемые колонки? раскрывающаяся строка-деталь?).
  Обсудить варианты ПЕРЕД кодом.

### 7E. (Дальние итерации) Мобильный интерфейс
- [ ] Адаптив под телефоны: навигация, таблица (карточный режим на узких экранах), формы.

### 7F. Авто-обновление таблицы при изменениях другого пользователя
- [ ] Сейчас таблица перечитывается только при действиях самого пользователя (refreshKey растёт
  после собственного сохранения; фильтры/поиск/страница). У ДРУГИХ открытых клиентов список
  НЕ обновляется — видят старые данные до ручного refresh/смены фильтра/перезагрузки.
- [ ] Polling нет, realtime нет (единственный setInterval — heartbeat локов в useLock.ts).
- [ ] **Решение (рекоменд.):** polling — таблица сама перечитывает список раз в 15-30 сек
  (setInterval → load()). Просто, без новой инфраструктуры. Учесть: не сбивать ввод поиска,
  не дёргать loading-спиннер на фоновых обновлениях (тихий refetch).
- [ ] Альтернативы (если polling мало): SSE (EventSource, сервер шлёт «данные изменились») или
  WebSocket-broadcast (нужен кастомный server.js — дороже).
- Связано с локами (итер. 5): локи защищают от одновременного редактирования одной записи и
  перезаписи (optimistic version → 409), но НЕ рассылают «список изменился».
