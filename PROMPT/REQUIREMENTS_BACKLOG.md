## 3. Карточка абитуриента (Applicant Form Modal)

### 3.1 Структура вкладок (переупорядочивание)
**Новый порядок:**
1. **Основное** (ФИО, программа, статус)
2. **Документы и согласие** ← Переместить сюда (было ниже)
   - Чекбокс "Документы собраны"
   - Чекбокс "Согласие на зачисление"

   - Чекбокс "Платно" ← Новое
   - Выпадающий список "Документ" (диплом/аттестат)

3. **Баллы экзаменов**
   - Математика (база) — оценка 2-5
   - Математика (профиль) — баллы 0-100
   - Русский, Химия, Физика, Информатика, География — баллы 0-100

4. **Контакты** (телефон, email)
5. **Персональное** (прописка, ИНН, СНИЛС, заметки)

## 10-bis. Итерация 7 (NEXT — собрано 2026-06-13)

### 7A. Дашборд: «движение согласий за день» должно ОБНОВЛЯТЬСЯ, а не накапливаться ✅ СДЕЛАНО
Реализовано: в stats/daily согласия за день считаются НЕТТО — по каждому абитуриенту
сравнивается состояние на начало дня (oldValue первого изменения) с состоянием на конец дня
(newValue последнего изменения); туда-сюда за день → 0.
- [x] **«Новые согласия сегодня»** показывают ЧИСТЫЙ итог за день (нетто), а не сумму переключений.
  - Если за день согласие забрали, а потом вернули → НЕ увеличивает «забрали».
  - Если за день согласие подали, а потом забрали → НЕ увеличивает «подали».
- [x] Считается по конечному состоянию против начального (а не сумма переключений из History).
- **Где:** `src/app/api/stats/daily/route.ts` (consentGivenToday/consentWithdrawnToday).

### 7G. История: показывать название программы, а не её ID ✅ СДЕЛАНО
Реализовано: formatHistoryValue получил опц. параметр programNames (Map id→name);
history-modal подтягивает программы и резолвит programId→название, фолбэк «Программа #id».
- [x] При изменении программы абитуриента в истории отображается **числовой programId**
  (напр. «3»), а не название программы («ИСД»). Нужно показывать название.
- **Причина:** в lib/history.ts поле `programId` логируется через toStr() как сырой id
  (oldValue/newValue = число). При показе в history-modal подмены id→название нет.
- **Варианты решения:**
  1. Резолвить id→название при ОТОБРАЖЕНИИ (history-modal): подтянуть список программ и
     маппить programId→name. Плюс: историч. записи не дублируют название; минус: если
     программу переименовали/удалили — старый id может не сматчиться.
  2. Логировать сразу название (в buildHistoryEntries для programId писать name вместо id).
     Плюс: запись самодостаточна; минус: нужно прокинуть имена программ в момент записи.
  - Рекоменд.: вариант 1 (резолв при показе) + фолбэк «Программа #<id>» если имя не найдено.
- Аналогично проверить другие FK/коды, если появятся (пока только programId).

### 7F. Авто-обновление таблицы при изменениях другого пользователя ✅ СДЕЛАНО
Реализовано: в applicant-table тихий polling — setInterval каждые 20 сек вызывает load(true)
(silent: без спиннера, без сброса строк при ошибке). load зависит от filters, поэтому
фоновый refetch уважает текущие фильтры/поиск/страницу.
- [x] Раньше таблица перечитывалась только при действиях самого пользователя; теперь видны
  изменения других клиентов без ручного refresh.
- [x] Тихий refetch: не дёргает loading-спиннер, не сбивает ввод поиска.
- [ ] Альтернативы (если polling мало): SSE (EventSource, сервер шлёт «данные изменились») или
  WebSocket-broadcast (нужен кастомный server.js — дороже).
- Связано с локами (итер. 5): локи защищают от одновременного редактирования одной записи и
  перезаписи (optimistic version → 409), но НЕ рассылают «список изменился».
